# 10. Justifications

## 1. Méthode de justification

Chaque décision technique de Phase 3 est documentée ici selon un
format synthétique :

- **Alternatives envisagées :** les options qui ont été examinées.
- **Critère principal :** ce qui a servi à trancher.
- **Arbitrage :** pourquoi l'option retenue l'emporte sur les autres.

Ce niveau de détail est volontairement synthétique. L'objectif est
de garantir la traçabilité des décisions sans produire de
documentation dont le coût dépasserait la valeur, conformément au
problème métier du projet.

Les décisions détaillées sont dans 08.Architecture.md et
09.Choix_Technos.md. Ce fichier ne les répète pas, il les justifie.

---

## 2. Justification de la stratégie de choix

**Stratégie retenue :** productivité maximale solo.

- **Alternatives envisagées :**
  - Stratégie "briques dominantes" (technos les plus utilisées du marché,
    même si plus lourdes).
  - Stratégie "réutilisation V2.2" (réemploi de la stack déjà validée
    sur le projet Créateur Contenu IA).
- **Critère principal :** cohérence directe avec le problème métier
  du projet, à savoir réduire le coût de production des preuves publiques.
- **Arbitrage :** un utilisateur unique (D-01) construisant un système
  destiné à produire régulièrement des preuves publiques doit optimiser
  le temps métier, pas le temps technique. Les deux autres stratégies
  ajoutaient soit de la charge cognitive inutile, soit une dette
  implicite de reconduction.

## 3. Justification par brique

### 3.1. Langage principal — TypeScript

- **Alternatives envisagées :** Python, Go.
- **Critère principal :** capacité à porter dans une seule stack
  à la fois l'UI et la logique applicative des 7 modules internes.
- **Arbitrage :** Python est faible pour construire une interface
  web productive. Go a un écosystème UI web trop restreint, ce qui
  aurait forcé une architecture front/back séparée, contradictoire
  avec le monolithe modulaire retenu. TypeScript couvre UI et logique
  avec un typage fort, réduisant le coût des erreurs.

### 3.2. Framework applicatif — Next.js

- **Alternatives envisagées :** Remix, NestJS avec frontend séparé.
- **Critère principal :** capacité à porter UI, routes API et logique
  dans une seule base de code cohérente (architecture monolithe modulaire).
- **Arbitrage :** NestJS impose un frontend distinct, ce qui casse
  l'architecture retenue. Remix est techniquement valable mais
  possède un écosystème plus restreint, donc moins de documentation
  et d'exemples, donc un coût cognitif plus élevé. Next.js maximise
  la productivité solo et bénéficie du plus grand écosystème.

### 3.3. Base de données — PostgreSQL via Supabase

- **Alternatives envisagées :** PostgreSQL managé pur (Neon, Railway),
  SQLite fichier local.
- **Critère principal :** minimiser le nombre de décisions techniques
  distinctes en couvrant plusieurs besoins avec un seul fournisseur.
- **Arbitrage :** SQLite est éliminé car incompatible avec une
  exposition publique performante (M7 Consultation). PostgreSQL
  managé pur oblige à choisir séparément l'authentification et le
  stockage de fichiers. Supabase couvre les trois besoins nativement,
  ce qui réduit la charge de décision et d'intégration.

### 3.4. Authentification — Supabase Auth

- **Alternatives envisagées :** NextAuth.js / Auth.js, Clerk, Auth0.
- **Critère principal :** intégration native avec la base de données
  choisie, sans ajout d'un fournisseur externe.
- **Arbitrage :** NextAuth impose un câblage manuel du stockage.
  Clerk et Auth0 sont disproportionnés pour un utilisateur unique.
  Supabase Auth est déjà inclus dans la brique 3, l'intégration est
  native, et les fonctionnalités couvrent largement le besoin actuel
  et son évolution raisonnable.

### 3.5. Hébergement et déploiement — Vercel

- **Alternatives envisagées :** Netlify, VPS auto-hébergé (Hetzner, OVH).
- **Critère principal :** support natif de Next.js et intégration
  automatique avec GitHub.
- **Arbitrage :** un VPS auto-hébergé impose une charge d'infra
  (reverse proxy, certificats, monitoring, backups) qui ruine la
  stratégie de productivité solo. Netlify est fonctionnel mais moins
  natif sur Next.js. Vercel est l'éditeur officiel du framework,
  donc aucun risque de support partiel des fonctionnalités.

  **Note :** le projet V2.2 (Créateur Contenu IA) tourne sur un
  hébergement différent (dashboard.sterveshop.cloud). Ce choix
  différent est cohérent car le contexte est différent : V2.2 servait
  à formuler la méthode, pas à minimiser le temps de production
  de preuves publiques.

### 3.6. CI/CD — GitHub Actions + Vercel

- **Alternatives envisagées :** Vercel seul, CI/CD externe
  (CircleCI, GitLab CI).
- **Critère principal :** garantir un filet de sécurité automatique
  sans ajouter de plateforme externe.
- **Arbitrage :** Vercel seul déploie ce qui est poussé, sans filtre
  qualité. Une CI/CD externe ajoute une plateforme sans bénéfice
  additionnel dans le contexte. GitHub Actions est intégré nativement
  au repo, gratuit dans les quotas standards, et complète Vercel
  proprement : GitHub Actions pour la CI qualité, Vercel pour le CD.

### 3.7. Gestion du code source — Git + GitHub

- **Alternatives envisagées :** aucune, décision figée en Phase 1.
- **Critère principal :** cohérence avec les décisions déjà prises
  en amont du projet.
- **Arbitrage :** cette brique n'est pas rejugée en Phase 3.
  Elle est documentée pour cohérence.

### 3.8. Instrumentation — Table events Supabase + logs Vercel

- **Alternatives envisagées :** service externe complet (PostHog,
  Sentry, Datadog), absence d'instrumentation dédiée.
- **Critère principal :** cohérence avec le fait que l'instrumentation
  métier est un objet du système (M5 Mesures) et non un service annexe.
- **Arbitrage :** l'absence d'instrumentation viole D-04 et CA-02,
  donc éliminée. Un service externe complet est disproportionné pour
  un utilisateur unique et déplace hors du système une capacité qui
  lui appartient. Une table `events` dans la base donne le contrôle
  total du modèle d'événement métier et reste native au système.
  Les logs techniques Vercel couvrent le besoin technique sans
  fournisseur additionnel.

## 4. Justification du style d'architecture

**Style retenu :** monolithe modulaire.

- **Alternatives envisagées :** frontend + backend séparés, microservices.
- **Critère principal :** cohérence avec les décisions figées
  (D-01 utilisateur unique, D-04 instrumentation, D-05 reproductibilité,
  D-06 version comme objet métier) et avec le problème métier
  (minimiser le temps de production des preuves publiques).
- **Arbitrage :** les microservices sont totalement disproportionnés
  pour un utilisateur unique et introduiraient une complexité
  d'orchestration qui ruinerait la valeur métier recherchée.
  L'architecture front/back séparée multiplie les déploiements et
  les points de friction sans bénéfice à ce stade. Le monolithe
  modulaire concilie simplicité de livraison et frontières internes
  strictes, ces frontières pouvant servir de base à une éventuelle
  extraction future si le système devient produit.

## 5. Arbitrages transverses

### 5.1. Pourquoi ne pas réutiliser intégralement la stack V2.2

- **Contexte :** V2.2 (Créateur Contenu IA) est le projet zéro
  qui a servi à formuler la méthode. Il utilise une stack déployée
  en auto-hébergement.
- **Critère principal :** V2.2 avait un contexte de recherche
  méthodologique, ce projet a un contexte de production continue
  de preuves publiques.
- **Arbitrage :** reconduire la stack V2.2 par confort figerait
  le futur sur du passé. Les choix ont été refaits à partir du
  problème métier actuel, ce qui est la démonstration même de la
  méthode : les décisions techniques découlent du besoin, pas
  de l'habitude.

### 5.2. Pourquoi privilégier systématiquement des services managés

- **Critère principal :** minimiser le temps non productif (infra,
  configuration, maintenance).
- **Arbitrage :** l'auto-hébergement offre plus de contrôle mais
  au prix d'une charge continue qui n'apporte aucune valeur métier
  à ce stade. La stratégie B (productivité maximale solo) exclut
  toute complexité qui ne sert pas directement la production de
  preuves publiques.

### 5.3. Pourquoi ne pas introduire de service tiers pour l'auth ou l'observabilité

- **Critère principal :** chaque fournisseur externe ajoute une
  décision, une intégration, un point de défaillance et parfois
  un coût.
- **Arbitrage :** tant que Supabase et Vercel couvrent les besoins
  correctement, aucun fournisseur additionnel n'est justifié.
  Cette position pourra être réévaluée si le système devient produit
  multi-utilisateurs.
