# 13. Stratégie de documentation

## 1. Objectif du document

Ce document définit la stratégie de documentation appliquée au système
Méthode Architecte IA.

Il ne contient pas la documentation elle-même.
Il définit :
- quels types de documentation existent,
- à qui chaque type s'adresse,
- où chaque type vit,
- à quel niveau de détail,
- selon quelles règles de mise à jour.

Cette stratégie repose sur une segmentation explicite en 3 axes :
utilisateur, technique, méthode.

---

## 2. Principes de documentation

**PD-01 — Segmentation par public**
La documentation est segmentée selon le public visé.
On refuse la doc unique qui prétend servir tous les publics à la fois.

**PD-02 — La doc méthode est aussi une preuve publique**
La documentation de méthode ne sert pas seulement à toi.
Elle sert aussi à démontrer publiquement la compétence.
Elle doit donc être lisible par un tiers externe sans contexte préalable.

**PD-03 — Reproductibilité obligatoire de la méthode**
La décision D-05 impose que la méthode soit reproductible.
La doc méthode doit permettre à un lecteur qualifié de comprendre
la démarche complète, sans accès au projet lui-même.

**PD-04 — Coût de la doc justifié par sa valeur**
Aucune doc n'est produite sans un public identifié et un usage clair.
On refuse la doc "au cas où".

**PD-05 — La doc vit avec le code**
La documentation évolue au rythme du code.
Une doc obsolète est un contre-signal : elle nuit à la confiance
dans le système.

**PD-06 — Simplicité assumée**
La stratégie doit rester tenable en solo dev.
Toute complexité ajoutée doit être justifiée par une valeur métier.

---

## 3. Les 3 axes de documentation

| Axe | Public visé | Rôle principal |
|---|---|---|
| Axe 1 — Utilisateur | Toi, en tant qu'utilisateur du système | Savoir utiliser le système au quotidien |
| Axe 2 — Technique | Toi, en tant que mainteneur du système | Faire évoluer le système sans le casser |
| Axe 3 — Méthode | Toi + tiers observateur externe | Comprendre et reproduire la méthode d'architecte IA |

---

## 4. Axe 1 — Documentation utilisateur

**Public**
Toi, en tant qu'utilisateur du système Méthode Architecte IA.

**Objectif**
Permettre d'utiliser le système au quotidien sans avoir à consulter
le code ou la doc technique.

**Emplacement**
Fichier Markdown dédié dans le repo : `docs/utilisateur.md`

**Format**
Markdown, sections courtes, orientées "comment faire".

**Niveau de détail**
Suffisant pour effectuer les actions clés du MVP :
- se connecter,
- créer un projet,
- suivre les étapes d'un projet,
- attacher un livrable à une étape,
- transformer un livrable en preuve publique,
- consulter les preuves publiées.

Pas de captures d'écran obligatoires en MVP.
Pas de tutoriels avancés.

**Ce qui n'y figure pas**
- Détails d'implémentation technique.
- Justifications de choix d'architecture.
- Description de la méthode elle-même.

---

## 5. Axe 2 — Documentation technique

**Public**
Toi, en tant que mainteneur du système.

**Objectif**
Permettre de faire évoluer le système, de le déployer, de le déboguer
et de comprendre ses choix techniques sans avoir à tout redécouvrir
à chaque intervention.

**Emplacement**
Dossier thématique dans le repo : `docs/technique/`

Fichiers attendus au fil des lots (liste non exhaustive) :
- `docs/technique/setup.md` — installation locale et prérequis
- `docs/technique/architecture.md` — vue technique de l'architecture modulaire
- `docs/technique/base_de_donnees.md` — schéma et conventions Supabase
- `docs/technique/deploiement.md` — pipeline CI/CD et déploiement Vercel
- `docs/technique/tests.md` — exécution des tests en local et en CI
- `docs/technique/depannage.md` — problèmes rencontrés et solutions

Chaque fichier reste court et actionnable.
On refuse le mégafichier technique unique.

**Format**
Markdown, sections courtes, orientées "comment ça marche" ou "comment intervenir".

**Niveau de détail**
Suffisant pour reprendre le projet après plusieurs mois d'absence
sans avoir à tout redécouvrir.

**Ce qui n'y figure pas**
- Manuel utilisateur.
- Description conceptuelle de la méthode (celle-ci vit dans l'axe 3).
- Réplication des commentaires du code source.

---

## 6. Axe 3 — Documentation méthode

**Public**
Toi (référence permanente) + tout observateur externe qualifié
(futur client, lecteur public, pair).

**Objectif**
Rendre la méthode d'architecte IA compréhensible, défendable
et reproductible par un tiers.

**Emplacement**
À la racine du repo, sous la forme des fichiers numérotés déjà en place :

- `00.README.md`
- `01.Besoin_Client.md`
- `02.Probleme_Metier.md`
- `03.Objets_Metier.md`
- `04.Objet_Central.md`
- `05.Cycle_de_Vie.md`
- `06.Composants.md`
- `07.Contrats.md`
- `08.Architecture.md`
- `09.Choix_Technos.md`
- `10.Justifications.md`
- `11.Plan_Implementation.md`
- `12.Strategie_Tests.md`
- `13.Documentation.md`

**Format**
Markdown, convention stricte `NN.Nom_Etape.md`.

**Niveau de détail**
Chaque étape doit être compréhensible par un tiers qualifié
sans accès au code du projet.
Chaque décision doit être justifiée.

**Rôle particulier**
Cet axe joue un double rôle :
- référence interne pour toi,
- preuve publique de compétence pour un observateur externe.

C'est pour cette raison qu'il vit à la racine du repo,
et pas dans un sous-dossier.

**Ce qui n'y figure pas**
- Manuel utilisateur.
- Détails techniques d'implémentation.
- Contenu de la doc technique.

## 7. Emplacement et format synthétique

| Axe | Emplacement | Format | Public |
|---|---|---|---|
| Utilisateur | `docs/utilisateur.md` | Markdown | Toi (usage) |
| Technique | `docs/technique/*.md` | Markdown | Toi (maintenance) |
| Méthode | Racine du repo, fichiers `NN.Nom_Etape.md` | Markdown | Toi + tiers externe |

## 8. Règles de mise à jour

**RM-01 — La doc utilisateur est mise à jour à la fin de chaque lot
qui change un parcours utilisateur.**
Aucun lot modifiant un parcours utilisateur ne peut être considéré
terminé sans mise à jour de `docs/utilisateur.md`.

**RM-02 — La doc technique est mise à jour à la fin de chaque lot
qui change un choix technique ou une procédure de maintenance.**
Aucun lot modifiant l'infrastructure, la base de données, le déploiement
ou la stratégie de tests ne peut être considéré terminé sans mise à jour
du fichier correspondant dans `docs/technique/`.

**RM-03 — La doc méthode évolue uniquement lors des séances de méthode.**
Les fichiers `NN.Nom_Etape.md` ne sont pas modifiés au fil de
l'implémentation courante.
Ils évoluent uniquement dans le cadre d'une révision explicite
de la méthode.

*Précision (S24) — Cocher une condition de sortie n'est pas une révision
de méthode.*
Changer `[ ]` en `[x]` dans une liste de conditions de sortie est un
**constat d'avancement**, autorisé hors séance de méthode, à deux conditions :
- seul le caractère de la case change ; toucher un seul mot d'un critère
  relève de RM-03 ;
- la case n'est cochée que contre une mesure effectuée et nommée au moment
  où on coche, jamais contre une conviction (leçon S23).

**RM-04 — La règle "build avant commit" s'applique aussi à la doc.**
Une doc modifiée doit être relue avant commit.
Toute incohérence détectée entre la doc et le code doit être résolue
avant le commit.

---

## 9. Conditions de sortie de la stratégie

La stratégie de documentation est considérée respectée pour le MVP quand :

- [ ] Le fichier `docs/utilisateur.md` existe et couvre les parcours clés du MVP.
- [ ] Le dossier `docs/technique/` existe et contient au minimum les fichiers
      `setup.md`, `architecture.md`, `base_de_donnees.md`, `deploiement.md`
      et `tests.md`.
- [ ] Les fichiers `NN.Nom_Etape.md` à la racine sont à jour et cohérents
      avec l'état réel de la méthode.
- [ ] Aucun lot du plan d'implémentation n'a été livré sans respecter
      les règles de mise à jour applicables.
- [ ] La doc méthode reste lisible par un tiers qualifié sans accès au code.
