# 12. Stratégie de tests

## 1. Objectif du document

Ce document définit la stratégie de tests appliquée au système
Méthode Architecte IA.

Il ne décrit pas comment coder les tests.
Il définit :
- ce qui doit être testé,
- à quel niveau,
- avec quels outils,
- selon quelles règles minimales.

Cette stratégie est asymétrique par choix : rigoureuse sur la chaîne
de valeur critique, légère sur le périphérique, absente sur les zones
sans valeur métier.

---

## 2. Principes de la stratégie de tests

**PT-01 — Asymétrie orientée valeur métier**
Les tests sont concentrés sur la chaîne critique de valeur.
Le reste est testé légèrement ou pas testé du tout.
On refuse la couverture uniforme.

**PT-02 — Fiabilité de la preuve publique avant tout**
Une preuve publique cassée en production est un contre-signal métier
direct. La chaîne qui mène à la preuve publique doit être testée E2E.

**PT-03 — Coût du test justifié par la valeur qu'il protège**
Aucun test n'est ajouté sans une raison métier claire.
Chaque test doit protéger une valeur observable.

**PT-04 — Tests intégrés à chaque lot**
Un lot n'est pas terminé sans les tests exigés par ses règles minimales
(voir section 8). Les tests ne sont pas ajoutés a posteriori.

**PT-05 — Automatisation obligatoire pour la chaîne critique**
Les tests de la chaîne critique doivent être exécutables automatiquement
en local et en CI. Aucun test critique ne repose sur une vérification
manuelle.

**PT-06 — Simplicité assumée**
La stratégie doit rester tenable en solo dev.
Toute complexité ajoutée doit être justifiée par une valeur métier.

---

## 3. Niveaux de tests utilisés

**N1 — Tests unitaires**
Vérifient une fonction ou un module isolé.
Rapides, nombreux là où c'est utile, absents là où ça n'apporte rien.

**N2 — Tests d'intégration légère**
Vérifient la coopération de plusieurs modules internes, sans navigateur.
Utilisés pour les points où plusieurs modules internes interagissent
(ex : logique métier + accès données).

**N3 — Tests end-to-end (E2E)**
Vérifient un parcours utilisateur complet dans un vrai navigateur.
Réservés à la chaîne critique de valeur.

---

## 4. Chaîne de valeur critique — priorité de test maximale

La chaîne critique est :
Projet → Étape méthode → Livrable → Preuve publique → Événement mesuré


Cette chaîne doit être :
- couverte par des tests unitaires sur la logique métier clé,
- couverte par des tests d'intégration légère sur les points d'interaction
  entre modules,
- couverte par au moins un test E2E qui reproduit le parcours complet
  d'un utilisateur authentifié jusqu'à la publication d'une preuve
  consultable publiquement.

Éléments obligatoirement testés :
- Création d'un Projet.
- Marquage d'une Étape comme terminée.
- Attachement d'un Livrable à une Étape.
- Transformation d'un Livrable en Preuve publique.
- Accessibilité publique de la Preuve publiée.
- Enregistrement des 4 événements clés dans la table `events`.

---

## 5. Zones à test léger

Ces zones sont testées, mais sans exigence de couverture forte.
Un test représentatif suffit.

- Composants d'interface non critiques (mise en page, affichage secondaire).
- Formulaires simples sans logique métier complexe.
- Pages de consultation interne (hors preuves publiques).
- Utilitaires de formatage ou d'affichage.

Règle appliquée : au moins un test représentatif par zone,
uniquement si un bug y aurait un impact utilisateur visible.

---

## 6. Zones non testées automatiquement

Ces zones sont assumées non couvertes par des tests automatisés.
Le risque est accepté explicitement.

- Styles visuels purs (CSS, thème, mise en forme).
- Textes statiques.
- Configuration d'environnement (vérifiée manuellement lors du déploiement).
- Scripts ponctuels de maintenance.
- Dépendances externes (Supabase Auth, Vercel) : on fait confiance
  à leur propre fiabilité, on ne les re-teste pas.

Justification : coût de test disproportionné par rapport au risque réel
et à la valeur métier protégée.

---

## 7. Outils retenus

| Niveau | Outil | Justification |
|---|---|---|
| N1 — Unitaires | Vitest | Natif TypeScript, rapide, très bien intégré à l'écosystème Next.js moderne, configuration minimale. Cohérent avec l'objectif de productivité maximale solo. |
| N2 — Intégration légère | Vitest | Le même outil couvre ce niveau sans introduire de complexité supplémentaire. |
| N3 — End-to-end | Playwright | Standard moderne, gratuit et open source, excellent support Next.js, permet de tester le rendu public exactement comme un visiteur externe le verrait. |

Aucun autre outil de test n'est introduit dans le MVP.

---

## 8. Règles minimales par lot

Chaque lot d'implémentation défini dans 11.Plan_Implementation.md doit
respecter les règles minimales suivantes avant d'être considéré terminé.

**Lot 0 — Socle technique**
- Le pipeline CI exécute au moins un lancement de test (même vide) sans erreur.
- Vitest est installé et fonctionnel.
- Playwright est installé et fonctionnel.

**Lot 1 — Authentification**
- Test unitaire sur la logique de protection des routes privées.
- Vérification manuelle documentée du parcours de connexion / déconnexion.

**Lot 2 — Gestion des Projets**
- Tests unitaires sur les règles métier du Projet (statuts, transitions).
- Test d'intégration légère sur la création d'un Projet en base.
- Vérification que l'isolation des données est respectée.

**Lot 3 — Suivi de Méthode**
- Tests unitaires sur les règles métier des Étapes et Livrables.
- Test d'intégration légère sur l'attachement d'un Livrable à une Étape.

**Lot 4 — Preuves publiques**
- Tests unitaires sur les règles métier de la Preuve publique (statuts, visibilité).
- Test d'intégration légère sur la transformation d'un Livrable en Preuve.
- **Test E2E obligatoire** : parcours complet depuis la création d'un Projet
  jusqu'à la consultation publique de la Preuve sans authentification.

**Lot 5 — Instrumentation**
- Tests unitaires vérifiant que chaque événement clé est bien émis.
- Test d'intégration légère vérifiant l'écriture effective dans la table `events`.

---

## 9. Conditions de sortie de la stratégie

La stratégie de tests est considérée respectée pour le MVP quand :

- [x] Vitest est opérationnel en local et en CI.
- [x] Playwright est opérationnel en local et en CI.
- [x] Les règles minimales de chaque lot (section 8) sont satisfaites.
- [x] Au moins un test E2E couvre la chaîne critique complète.
- [x] Aucun test critique ne repose sur une vérification manuelle.
- [x] Les zones non testées automatiquement sont explicitement listées
      et le risque est assumé.
