# 11. Plan d'implémentation

## 1. Objectif du document

Ce document définit comment le MVP du système Méthode Architecte IA sera
construit : dans quel ordre, selon quels principes de découpage, et à partir
de quels critères chaque lot est considéré comme terminé.

Ce plan précède toute implémentation. Il ne décrit pas le code.
Il décrit la séquence de livraison de valeur métier.

---

## 2. Principes de découpage

**P-01 — Tranches verticales de valeur**
Chaque lot doit produire une capacité métier utilisable de bout en bout,
même si les lots suivants ne sont pas encore construits.
Un lot "base de données seule" ou "interface seule" n'est pas acceptable.

**P-02 — Objet central en premier**
L'objet central du système est le Projet. Toute construction qui ne sert
pas directement la chaîne Projet → Étapes → Preuve → Mesure est reportée
après le MVP.

**P-03 — Instrumentation intégrée dès le début**
La décision D-04 impose un système obligatoirement instrumenté.
L'instrumentation n'est pas un lot séparé ajouté en fin de MVP.
Elle est intégrée dans chaque lot dès le premier.

**P-04 — Hors MVP explicitement nommé**
Tout ce qui n'est pas dans les lots listés est explicitement hors MVP.
Aucune fonctionnalité ne rentre dans le MVP sans décision explicite.

**P-05 — Critère de sortie obligatoire**
Aucun lot ne peut être considéré terminé sans que ses critères de sortie
soient satisfaits. Un critère de sortie est toujours observable et vérifiable.

---

## 3. Définition du MVP visé

Le MVP est la version minimale du système qui permet de :

1. Créer et gérer un Projet.
2. Suivre les étapes de méthode d'un Projet.
3. Attacher un Livrable à une étape.
4. Produire et exposer publiquement une Preuve liée à un Livrable.
5. Mesurer les événements clés de la chaîne de valeur.

Le MVP est considéré atteint quand cette chaîne complète fonctionne
de bout en bout pour un utilisateur unique authentifié.

**Ce que le MVP n'est pas :**
- Un système multi-utilisateurs.
- Un système de gestion de missions et clients complet.
- Un système de diffusion automatisée sur les canaux externes.
- Un tableau de bord analytique avancé.

---

## 4. Ordre général de construction


| Lot | Nom | Valeur métier produite |
|-----|-----|------------------------|
| Lot 0 | Socle technique | Rien de visible, mais tout le reste peut être construit |
| Lot 1 | Authentification | L'utilisateur peut accéder à son espace sécurisé |
| Lot 2 | Gestion des Projets | L'utilisateur peut créer et gérer ses projets |
| Lot 3 | Suivi de Méthode | L'utilisateur peut suivre les étapes d'un projet |
| Lot 4 | Preuves publiques | L'utilisateur peut produire et exposer une preuve |
| Lot 5 | Instrumentation | Le système mesure les événements clés |

## 5. Lots d'implémentation

---

### Lot 0 — Socle technique

**Objectif**
Mettre en place l'infrastructure technique minimale sur laquelle tous
les lots suivants s'appuient.

**Périmètre**
- Initialisation du projet Next.js avec TypeScript.
- Configuration Supabase (projet, base de données, variables d'environnement).
- Connexion Next.js ↔ Supabase vérifiée.
- Déploiement initial sur Vercel (environnement de production vide).
- Pipeline CI/CD GitHub Actions → Vercel opérationnel.
- Structure de dossiers conforme à l'architecture modulaire définie en Phase 3.

**Dépendances**
- Aucune. C'est le point de départ.

**Critères de sortie**
- [x] Le projet Next.js démarre localement sans erreur.
- [x] La connexion à Supabase est vérifiée (requête de test réussie).
- [x] Le déploiement Vercel fonctionne depuis un push sur la branche principale.
- [x] Le pipeline CI/CD exécute au moins une vérification automatique (lint ou build).
- [x] La structure de dossiers respecte l'architecture modulaire définie en 08.Architecture.md.

**Valeur métier apportée**
Nulle directement. Mais sans ce lot, aucun autre lot ne peut être construit.
Ce lot est le prérequis technique de toute la chaîne de valeur.

---

### Lot 1 — Authentification

**Objectif**
Permettre à l'utilisateur unique de se connecter et d'accéder à son espace
personnel de manière sécurisée.

**Périmètre**
- Intégration Supabase Auth (email + mot de passe).
- Page de connexion.
- Protection des routes privées.
- Déconnexion.
- Session persistante.

**Dépendances**
- Lot 0 terminé.

**Critères de sortie**
- [x] L'utilisateur peut se connecter avec email + mot de passe.
- [x] Les routes privées sont inaccessibles sans authentification.
- [x] La session persiste après rafraîchissement de page.
- [x] L'utilisateur peut se déconnecter.
- [x] Aucune donnée privée n'est accessible sans session active.

**Valeur métier apportée**
L'utilisateur peut accéder à son espace sécurisé.
La décision D-01 (utilisateur unique) est respectée : aucun système
d'inscription publique n'est prévu.

---

### Lot 2 — Gestion des Projets

**Objectif**
Permettre à l'utilisateur de créer, consulter, modifier et archiver ses projets.

**Périmètre**
- Modèle de données : table `projects` dans Supabase.
- CRUD complet sur les Projets (Create, Read, Update, Delete/Archive).
- Liste des projets.
- Détail d'un projet.
- Statuts de cycle de vie du Projet tels que définis en 05.Cycle_de_Vie.md.

**Dépendances**
- Lot 0 terminé.
- Lot 1 terminé.

**Critères de sortie**
- [x] L'utilisateur peut créer un projet avec les champs définis dans 03.Objets_Metier.md.
- [x] L'utilisateur peut consulter la liste de ses projets.
- [x] L'utilisateur peut consulter le détail d'un projet.
- [x] L'utilisateur peut modifier un projet.
- [x] L'utilisateur peut archiver un projet.
- [x] Les statuts de cycle de vie sont respectés.
- [x] Aucun projet d'un autre utilisateur n'est accessible (isolation des données).

**Valeur métier apportée**
L'objet central du système est opérationnel.
La chaîne de valeur peut commencer à être construite.

---

### Lot 3 — Suivi de Méthode

**Objectif**
Permettre à l'utilisateur de suivre les étapes de méthode d'un projet
et d'y attacher des livrables.

**Périmètre**
- Modèle de données : tables `method_steps` et `deliverables` dans Supabase.
- Affichage des étapes de méthode pour un projet donné.
- Marquage d'une étape comme terminée.
- Attachement d'un Livrable à une étape (titre, description, lien ou fichier).
- Statuts de cycle de vie des Étapes et Livrables.

**Dépendances**
- Lot 0 terminé.
- Lot 1 terminé.
- Lot 2 terminé.

**Critères de sortie**
- [x] Les étapes de méthode sont affichées pour un projet donné.
- [x] L'utilisateur peut marquer une étape comme terminée.
- [x] L'utilisateur peut attacher un livrable à une étape.
- [x] Le livrable est consultable depuis le détail de l'étape.
- [x] Les statuts de cycle de vie des étapes sont respectés.

**Valeur métier apportée**
L'utilisateur peut suivre sa progression sur un projet réel.
La méthode devient un outil de suivi actif, pas seulement un document.

---

### Lot 4 — Preuves publiques

**Objectif**
Permettre à l'utilisateur de transformer un livrable en preuve publique
exposée sur le point d'accès public du système (M7 Consultation).

**Périmètre**
- Modèle de données : table `public_proofs` dans Supabase.
- Action : transformer un livrable en preuve publique.
- Page publique listant les preuves publiées (accessible sans authentification).
- Page publique de détail d'une preuve.
- Statuts : brouillon / publié / archivé.

**Dépendances**
- Lot 0 terminé.
- Lot 1 terminé.
- Lot 2 terminé.
- Lot 3 terminé.

**Critères de sortie**
- [x] L'utilisateur peut transformer un livrable en preuve publique.
- [x] La preuve publique est accessible sans authentification via une URL publique.
- [x] La liste des preuves publiées est visible publiquement.
- [x] Le détail d'une preuve est visible publiquement.
- [x] Une preuve en brouillon n'est pas accessible publiquement.
- [x] Une preuve archivée n'est plus accessible publiquement.

**Valeur métier apportée**
C'est le cœur de l'objectif stratégique du projet :
produire des preuves publiques de compétence.
Ce lot rend le système utile pour attirer des missions.

---

### Lot 5 — Instrumentation

**Objectif**
Mesurer les événements clés de la chaîne de valeur pour permettre
l'amélioration continue de la méthode (décision D-04).

**Périmètre**
- Modèle de données : table `events` dans Supabase.
- Enregistrement automatique des événements clés :
  - Projet créé.
  - Étape terminée.
  - Livrable attaché.
  - Preuve publiée.
- Consultation interne des événements (vue simple, pas de dashboard analytique).

**Dépendances**
- Lots 0 à 4 terminés.

**Critères de sortie**
- [x] Les 4 événements clés sont enregistrés automatiquement dans la table `events`.
- [x] Chaque événement contient : type, horodatage, identifiant de l'objet source.
- [x] Les événements sont consultables en interne.
- [x] Aucun événement privé n'est exposé publiquement.

**Valeur métier apportée**
Le système peut maintenant mesurer la cadence de production réelle
(décision D-03 : cadence non fixée a priori, à mesurer).
La décision D-04 est pleinement respectée.

---

## 6. Éléments explicitement hors MVP

Les éléments suivants ne font pas partie du MVP.
Ils pourront être ajoutés dans des versions ultérieures si la valeur
métier le justifie.

| Élément | Raison de l'exclusion |
|---|---|
| Gestion des Missions et Clients (C6) | Valeur métier non prioritaire pour l'objectif initial |
| Diffusion automatisée sur canaux externes (C4) | Complexité disproportionnée par rapport à la valeur MVP |
| Dashboard analytique avancé | Hors périmètre MVP, les logs Vercel suffisent en phase initiale |
| Multi-utilisateurs | Décision D-01 : utilisateur unique |
| Système d'inscription publique | Décision D-01 : utilisateur unique |
| Gestion de fichiers uploadés | Report possible en post-MVP (lien externe suffisant) |
| Notifications / alertes | Aucune valeur métier identifiée pour le MVP |
| API publique | Non nécessaire pour le MVP |

---

## 7. Conditions de sortie du plan MVP

Le MVP est considéré terminé et le système est prêt pour une
première utilisation réelle quand :

- [x] Les lots 0 à 5 ont tous leurs critères de sortie satisfaits.
- [x] La chaîne complète Projet → Étapes → Livrable → Preuve publique
      fonctionne de bout en bout en production.
- [x] Au moins un projet réel a été créé, suivi et a produit une preuve publique.
- [x] Les événements clés sont bien enregistrés dans la table `events`.
- [x] Le système est déployé sur Vercel en production avec le domaine cible.
- [x] La stratégie de tests définie en 12.Strategie_Tests.md est respectée.
- [x] La documentation définie en 13.Documentation.md est à jour.
