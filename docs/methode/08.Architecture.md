# 08. Architecture

## 1. Style d'architecture retenu

**Style : Monolithe modulaire**

Le système est construit comme une seule application cohérente,
organisée en modules internes distincts et bien délimités.

Chaque module correspond à un composant fonctionnel défini en Phase 2.
Les modules communiquent entre eux via des contrats internes explicites,
définis dans 07.Contrats.md.

**Pourquoi ce choix à ce stade :**
- Utilisateur initial unique (D-01) : aucun besoin de distribution complexe.
- Objectif métier principal : réduire le coût de production des preuves publiques.
  Une architecture simple maximise le temps disponible pour produire de la valeur.
- Instrumentation obligatoire (D-04) : plus simple à intégrer dans un système unifié.
- Reproductibilité obligatoire (D-05) : une seule base applicative réduit
  la surface de configuration à reproduire.
- Version comme objet métier (D-06) : plus simple à implémenter proprement
  dans un système unifié que dans un système distribué.

**Évolution possible :**
Si le système est productisé (multi-utilisateurs, multi-tenants),
les frontières de modules posées ici serviront de base naturelle
pour extraire des services indépendants sans refonte complète.

## 2. Découpage en modules

Le système est découpé en 7 modules internes, alignés sur les
7 composants fonctionnels définis dans 06.Composants.md.

| Module | Composant source | Responsabilité principale |
|--------|-----------------|--------------------------|
| M1 — Projets | C1 — Gestion des Projets | Créer, suivre et archiver les projets |
| M2 — Méthode | C2 — Suivi de Méthode | Suivre l'avancement des étapes méthode |
| M3 — Preuves | C3 — Production de Preuves | Générer et stocker les livrables d'étape |
| M4 — Diffusion | C4 — Diffusion | Gérer les canaux et les publications |
| M5 — Mesures | C5 — Instrumentation | Collecter et exposer les métriques |
| M6 — Missions | C6 — Gestion des Missions et Clients | Gérer missions, clients, opportunités |
| M7 — Consultation | C7 — Consultation | Exposer les données publiques du système |

**Règle de découpage :**
Chaque module est responsable de ses propres données.
Un module ne lit pas directement les données d'un autre module.
Tout échange passe par un contrat défini (voir 07.Contrats.md).

## 4. Flux principaux entre modules

Les flux ci-dessous sont issus directement des contrats définis
dans 07.Contrats.md. Cette section les représente sous forme
de lecture architecturale.

| Flux | De | Vers | Déclencheur |
|------|----|------|-------------|
| F1 | M1 Projets | M2 Méthode | Création d'un projet |
| F2 | M2 Méthode | M3 Preuves | Validation d'une étape méthode |
| F3 | M3 Preuves | M4 Diffusion | Production d'un livrable d'étape |
| F4 | M4 Diffusion | M5 Mesures | Publication sur un canal |
| F5 | M5 Mesures | M7 Consultation | Agrégation d'une mesure |
| F6 | M6 Missions | M1 Projets | Création d'une mission associée |
| F7 | M1 Projets | M5 Mesures | Changement d'état d'un projet |
| F8 | M3 Preuves | M7 Consultation | Livrable publié |
| F9 | M2 Méthode | M5 Mesures | Étape terminée ou livrable attaché |
| F10 | M3 Preuves | M5 Mesures | Preuve publique publiée |

**Règle de flux :**
Aucun flux ne court-circuite un module.
Tout flux suit le chemin défini par les contrats.

## 5. Contraintes d'architecture

Les contraintes suivantes sont non négociables.
Elles découlent directement des décisions figées (D-01 à D-06).

| Contrainte | Source | Description |
|-----------|--------|-------------|
| CA-01 | D-01 | Le système est conçu pour un utilisateur initial unique. Aucune complexité multi-tenant n'est introduite à ce stade. |
| CA-02 | D-04 | L'instrumentation est obligatoire. Tout événement métier significatif doit être tracé. |
| CA-03 | D-05 | L'architecture doit être reproductible. La configuration du système doit pouvoir être reconstituée depuis le dépôt. |
| CA-04 | D-06 | La version de méthode est un objet métier. L'architecture doit permettre de versionner la méthode utilisée par chaque projet. |
| CA-05 | Métier | M7 Consultation est le seul point d'exposition publique. Aucun autre module n'expose de données publiques directement. |
| CA-06 | Métier | Les frontières de modules sont strictes. Aucun module n'accède directement aux données d'un autre module. |

## 6. Convention de structure de code interne

Chaque module vit sous `src/modules/mX-nom/` avec une sous-structure fixe :
`domain/` (règles métier, transitions d'état), `actions/` (Server Actions),
`queries/` (lecture), `ui/` (composants), `types.ts`.

Cette convention est documentée de façon normative dans `CLAUDE.md`
(racine du dépôt), pas dans ce fichier : elle relève d'un choix
d'implémentation (Phase 3), pas d'une décision de découpage métier.
Ce fichier garde uniquement ce renvoi explicite, pour que la frontière
entre "ce que la méthode décide" (le découpage M1-M7 et ses contrats,
ce fichier) et "comment le code l'implémente" (l'arborescence de
fichiers, `CLAUDE.md`) reste nette.
