# 09. Choix Technos

## 1. Stratégie de choix

**Stratégie retenue : productivité maximale solo.**

Cette stratégie privilégie les technologies qui permettent à un développeur
seul d'avancer le plus vite possible sur la valeur métier, en s'appuyant
sur des services managés pour minimiser la charge d'infrastructure.

Elle découle directement du problème métier :
> "Un architecte IA compétent reste invisible aux yeux du marché parce
> que chaque preuve publique de compétence exige un temps de production
> disproportionné par rapport au temps de réalisation du projet lui-même."

Toute techno qui augmenterait le temps non productif est écartée.
Toute techno qui augmenterait la vitesse de production de preuves
publiques est privilégiée.

Les justifications détaillées de chaque choix, y compris les alternatives
envisagées et les arbitrages, sont dans 10.Justifications.md.

## 3. Détail par brique

### 3.1. Langage principal

- **Techno :** TypeScript
- **Rôle :** langage unique du système, utilisé pour tous les modules
  (M1 à M7) ainsi que pour la couche UI.
- **Version cible :** dernière version stable majeure supportée par Next.js.

### 3.2. Framework applicatif

- **Techno :** Next.js
- **Rôle :** framework applicatif principal. Porte simultanément l'UI,
  les routes API internes et la logique des 7 modules internes,
  dans une seule base de code (architecture monolithe modulaire).
- **Version cible :** dernière version stable majeure.
- **Rendu :** support du rendu serveur natif utilisé notamment
  par M7 Consultation.

### 3.3. Base de données

- **Techno :** PostgreSQL, service managé Supabase.
- **Rôle :** stockage persistant unique et centralisé pour l'ensemble
  des modules. Chaque module est propriétaire de ses tables.
- **Version cible :** version PostgreSQL fournie par défaut par Supabase.
- **Accès :** via la couche fournie par Supabase et les règles
  Row Level Security.

### 3.4. Authentification

- **Techno :** Supabase Auth
- **Rôle :** authentification de l'utilisateur unique (D-01) pour
  accéder aux modules privés. M7 Consultation reste public sans auth.
- **Fonctionnalités utilisées à ce stade :** email/password.
  Les autres méthodes (magic link, OAuth) sont disponibles si besoin
  ultérieur.

### 3.5. Hébergement et déploiement

- **Techno :** Vercel
- **Rôle :** hébergement de l'application Next.js, déploiement
  automatique déclenché à chaque push GitHub.
- **Environnements :**
  - Production : branche principale.
  - Preview : par branche, si utilisées.
- **Tier :** gratuit à ce stade, largement suffisant pour l'usage prévu.

### 3.6. CI/CD

- **CI :** GitHub Actions
  - Rôle : vérifications qualité à chaque push (build, lint,
    et tests quand ils existeront).
- **CD :** Vercel
  - Rôle : déploiement automatique à chaque push sur la branche cible.
- **Cohérence avec la règle "BUILD AVANT COMMIT" :** cette règle
  reste applicable en local. La CI GitHub Actions constitue un
  second filet de sécurité automatique.

### 3.7. Gestion du code source

- **Techno :** Git + GitHub.
- **Repo :** https://github.com/sterve9/methode-architecte-ia
- **Visibilité :** public.
- **Convention de nommage des fichiers méthode :** NN.Nom_Etape.md.
- **Point acté en Phase 1 :** aucune décision nouvelle en Phase 3.

### 3.8. Instrumentation

- **Instrumentation métier :** table `events` dans Supabase.
  - Rôle : trace des événements métier significatifs, exploitables
    par M5 Mesures.
  - Exemples d'événements attendus : création de projet, validation
    d'une étape méthode, publication d'un livrable, agrégation
    d'une mesure.
  - Justification structurelle : l'instrumentation métier étant
    elle-même un objet du système, elle vit dans la base du système
    et non dans un service tiers.
- **Instrumentation technique :** logs Vercel natifs.
  - Rôle : logs applicatifs, erreurs runtime, performance.
  - Aucun service tiers ajouté à ce stade.

## 4. Contraintes de versions

- Toute techno utilisée doit être en **version stable majeure officielle**.
- Aucune version bêta, RC ou expérimentale.
- Les versions exactes retenues au moment de l'implémentation seront
  figées dans le fichier de dépendances du projet (package.json)
  et documentées si un changement structurant est décidé plus tard.
- La règle "zéro invention" impose de vérifier la documentation
  officielle avant toute utilisation d'un nom de fichier, d'une
  fonction ou d'une variable d'environnement liée à ces technos.
